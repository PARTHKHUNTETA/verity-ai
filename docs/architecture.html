VerityAI Backend — Architecture

VerityAI — Evaluated Research Agent · Research with evidence. Answers with confidence.

How the backend works: the processes, what happens when a request comes in, how a research run flows through the system, the database design, and where to change things. Everything here describes the code in this repository; file paths are relative to the repo root.

A viewable version of this document is generated with npm run docs:build → docs/architecture.html (open it in a browser).

#1. Overview

The backend is a modular monolith in TypeScript with two processes built from the same code:

ProcessEntry pointJob
APIsrc/server.ts → src/app.tsHTTP API under /api/v1: auth, research tasks, sources, reports, evaluations, policies. Streams live run progress (SSE). Never does slow AI work itself.
Workersrc/worker.tsBackground jobs: research runs (the agent), document ingestion, offline eval runs, maintenance sweeps.
Both (optional)src/all.tsRuns the API and the worker as two child processes in one container (PROCESS=all), for hosts where they can't share a disk.

They talk only through Postgres: rows, a job queue (pg-boss) and LISTEN/NOTIFY events. No Redis, no message broker.

#2. Architecture

flowchart LR
    Browser["Browser (React app)"] -->|"/api/v1 JSON, SSE"| Nginx["nginx (frontend image)"]
    Nginx -->|proxy /api| API["API process<br/>Express"]
    API -->|"rows (Drizzle)"| PG[("PostgreSQL 16<br/>tables + pgvector")]
    API -->|"enqueue jobs"| Q[["pg-boss queues<br/>research.run · source.ingest · eval.run"]]
    API -->|LISTEN run_events| PG
    Q --> Worker["Worker process<br/>agent runtime"]
    Worker -->|"rows, spans, NOTIFY"| PG
    Worker -->|LLM calls| OpenAI["OpenAI API"]
    Worker -->|search| Search["Tavily · arXiv · Semantic Scholar"]
    Worker -->|"safe fetch (public IPs only)"| Web["Web pages / PDFs"]
    API -->|"store uploads"| Disk[("Upload storage<br/>STORAGE_DIR")]
    Worker -->|"read uploads"| Disk
  • The API validates, authorizes, stores and enqueues. It answers in milliseconds.
  • The worker does everything slow or expensive: LLM calls, searching, fetching, parsing, embedding, evaluating.
  • Postgres is the single source of truth. Events (NOTIFY) only make the UI live; if one is missed, the next snapshot from the database is still correct.
  • Uploaded files live on disk (STORAGE_DIR), shared by both processes.

#4. When a request comes in

#4.1 The middleware chain (src/app.ts)

flowchart TD
    A["Request"] --> B["requestId<br/>x-request-id on req and response"]
    B --> C["requestLogger<br/>pino-http, one line per request"]
    C --> D["helmet<br/>security headers, strict CSP"]
    D --> E{"CORS_ORIGINS set?"}
    E -->|yes| F["cors (credentials)"]
    E -->|no| G
    F --> G["express.json (1 MB limit)"]
    G --> H["cookieParser"]
    H --> I["/api/v1 + apiRateLimit<br/>600 req/min per IP"]
    I --> J["module router"]
    J --> K["authenticate<br/>Bearer JWT → req.auth (user, org, role from DB)"]
    K --> L["requirePermission(action)<br/>RBAC check"]
    L --> M["validate({ params, query, body })<br/>zod"]
    M --> N["per-user rate limit<br/>(runs, evals, uploads, exports)"]
    N --> O["controller → service → repository"]
    O --> P[("Postgres")]
    O --> R["JSON response"]
    J -.->|"no route"| X["notFound → 404"]
    K -.->|throws| Y["errorHandler"]
    L -.->|throws| Y
    M -.->|throws| Y
    O -.->|throws| Y
  • Order matters: the request id comes first so every log line and error response carries it.
  • Public routes (/health, /auth/*) skip authenticate.
  • authenticate verifies the access token and reloads the membership from the database, so a removed member or a changed role takes effect immediately.
  • requirePermission maps the role to allowed actions (src/modules/policies/permissions.ts).
  • Uploads add multer (in memory, ≤ MAX_UPLOAD_MB) after validation.

#4.4 Authentication flow (src/modules/auth)

sequenceDiagram
    participant B as Browser
    participant A as API /auth
    participant DB as Postgres
    B->>A: POST /auth/login {email, password}
    A->>DB: user by email, verify argon2id hash
    A->>DB: insert refresh token (hash only, new family)
    A-->>B: access JWT (15 min, kept in memory) + refresh cookie (httpOnly, SameSite=strict, /api/v1/auth)
    Note over B: later, the access token expires
    B->>A: POST /auth/refresh (cookie)
    A->>DB: find token by hash, revoke it ("rotated"), insert the next one in the same family
    A-->>B: new access JWT + new refresh cookie
    Note over A,DB: a token that was already rotated comes back → revoke the whole family ("reuse_detected"), audit log

Login and register: 10 attempts per 15 minutes per IP; refresh and logout: 60 per 15 minutes.

#5. A research run, end to end

Starting research is fast; the work happens in the worker; progress streams back over SSE.

sequenceDiagram
    participant B as Browser
    participant API as API
    participant DB as Postgres
    participant Q as pg-boss
    participant W as Worker (agent runtime)
    participant LLM as OpenAI / search
    B->>API: POST /research/tasks {question, discover}
    API->>DB: insert research_task + research_run (status queued, config snapshot)
    API->>Q: enqueue research.run {runId}
    API-->>B: 201 {task, run}
    B->>API: GET /research/runs/:id/stream (SSE)
    API->>DB: LISTEN run_events, then send "snapshot"
    Q->>W: job research.run
    W->>DB: claim run (queued → running)
    loop each stage
        W->>DB: stage = X, NOTIFY status
        DB-->>API: event
        API-->>B: "status" + fresh "snapshot"
        W->>LLM: model / tool calls (through the policy gateway)
        W->>DB: rows (sub_questions, evidence, …), agent_steps, trace spans, state checkpoint
    end
    W->>DB: report text in chunks, NOTIFY "delta" {offset, text, version}
    DB-->>API: delta events
    API-->>B: "delta" (the answer streams in)
    W->>DB: scorecard, status completed, NOTIFY
    API-->>B: final "snapshot" + "done"

#5.2 Run control

  • State and resume: after every stage the runtime saves research_runs.state (completed stages, step count, usage, passages). The research.run queue has a 60 s heartbeat and one retry; if a worker dies, the retry resumes from the last completed stage.
  • Budgets (agent/budget.ts): max steps (60), tokens (400k), cost ($1), time (10 min) by default; the org policy and the run config can change them. Out of budget either fails the run or asks for approval (policy onExceed).
  • Cancel: POST /research/runs/:id/cancel sets the status and publishes an event; the worker aborts the in-flight LLM call.
  • Approval pause: a tool call that needs approval stores an approvals row and the run goes to awaiting_approval; deciding re-queues it and it continues where it stopped.
  • Stalled runs: a sweep marks runs with no checkpoint for 30 minutes as failed (STALLED).
  • SSE protocol (research/research.sse.ts): snapshot (full run detail), status, delta {offset, text, version} (version 2 = the revision), done. The API subscribes before reading the first snapshot, so no event is lost in between.

#6. Tool calls and the policy gateway

Stages never call tools directly: every call goes through ctx.tools.call → policies/executor.ts → policies/policy-gateway.ts.

flowchart TD
    A["Stage wants a tool<br/>search · fetch · rag · run_code"] --> B{"Same call already done<br/>in this run? (args_hash)"}
    B -->|succeeded| C["Return stored result"]
    B -->|waiting for approval| D{"Approval decided?"}
    D -->|approved| RUN
    D -->|"rejected / expired"| DENY
    D -->|pending| PAUSE
    B -->|new| E["Gateway checks, in order:<br/>tool enabled → arguments valid → user permission<br/>→ org rules (domains, per-run limits) → budget"]
    E --> F["Store tool_call + policy_decision"]
    F --> G{"Decision"}
    G -->|allow| RUN["Run with timeout and retries<br/>(span tool.*)"]
    G -->|deny| DENY["Skip, return the reason to the stage"]
    G -->|require approval| H{"Unattended run?<br/>(offline eval)"}
    H -->|yes| DENY
    H -->|no| PAUSE["Create approval, pause the run"]

Platform-wide domain rules (BLOCKED_DOMAINS, ALLOWED_DOMAINS) apply on top of each organization's policy (policies table, versioned).

#7. Retrieval and ingestion

flowchart LR
    U["Upload<br/>POST /collections/:id/sources"] --> S1["store file<br/>(SHA-256 dedupe)"]
    S1 --> J["source.ingest job"]
    D["Discovery (acquiring stage)"] --> F["safe fetch"] --> P
    J --> P["parse<br/>PDF pages · HTML Readability · text"]
    P --> C["chunk<br/>~800 tokens with overlap"]
    C --> E["embed<br/>text-embedding-3-small"]
    E --> T[("source_chunks<br/>vector + tsvector")]
    Q["Query"] --> V["vector search<br/>HNSW cosine"]
    Q --> K["full-text search<br/>GIN tsvector"]
    V --> RRF["reciprocal rank fusion"]
    K --> RRF
    T --> V
    T --> K
    RRF --> R["ranked passages"]
  • Safe fetch (infrastructure/http/safe-fetch.ts): http(s) only, ports 80/443, DNS resolved and every address checked (no private, loopback, link-local or metadata ranges), connection pinned to the checked IP, every redirect re-checked (max 5), size and time limits.
  • Dedupe: by content hash and canonical URL per organization; the same document is stored and embedded once and linked to several collections.
  • Access: a run only searches the collections its creator could read when it started (decided by the API and stored in the run config).

#8. Evaluation

#8.1 Online (every run, stage evaluating)

  1. Claim judge (evaluation/prompts/claim-judge.ts): each cited sentence vs. only the quotes it cites → supported / partial / unsupported, per-citation verdicts, rationale.
  2. Task judge: how completely the report does what was asked.
  3. Deterministic scorers (evaluation/scorers/): citation validity, coverage, source reliability, contradiction handling, policy compliance.
  4. Revision loop: claim support < 90 % → rewrite once with the flagged claims (revise-v1), judge again, keep the better version (the other is superseded).
  5. Scorecard → run_scorecards; readers can rate reports and claims (feedback).

#8.2 Offline (benchmarks, evaluation/offline/)

  • Datasets of cases (question, required points, expected/forbidden sources, forbidden content, category). POST /evals/datasets/starter installs a 25-case benchmark with fixture documents.
  • POST /evals/runs freezes a config (model, prompt versions, policy version, top K, discovery, revision, collections) and enqueues eval.run. The runner executes each case through the same agent runtime, unattended, then scores it (case-scorers.ts). Red-team cases are gated on security checks only.
  • Summaries and comparisons (summary.ts); the CLI npm run eval runs the same in-process for CI.

#9. Database design

#9.1 Conventions

  • Ids: UUID v7 (time-ordered) generated in the app (schema/columns.ts).
  • Tenancy: every tenant-owned table has organization_id; every query filters by it.
  • Timestamps: created_at / updated_at as timestamptz.
  • Naming: snake_case in SQL, camelCase in TypeScript (Drizzle casing: "snake_case").
  • Deletes: cascades from parent to children; soft delete (deleted_at) only on sources, collections and research_tasks.
  • Schema source: src/infrastructure/database/schema/*.ts; migrations generated with npm run db:generate into migrations/, applied with npm run db:migrate or npm run db:setup.

#9.6 Observability

trace_spans holds every span (trace id = run id): name, parent, attributes (model, tokens, cost, tool, decision), status, timings. It is partitioned by month on start_time (hand-edited migration 0008); the worker creates upcoming months and drops months older than 30 days.

#11. Observability

  • modules/observability/tracer.ts: inSpan starts a root span (run, one per attempt), withSpan nests under the current span via AsyncLocalStorage, so any code inside a run is traced without passing span objects around. Spans are buffered and written in batches.
  • Span names: run, stage.<stage>, llm.<method> (model, tokens, cost, time to first token), tool.<name>, policy.check, parse, ingest.index, llm.embed.
  • GET /research/runs/:id/trace returns the spans plus a summary (time and cost per stage, slowest operations); GET /observability/metrics?days=7|30|90 aggregates latency percentiles, tool errors, denials, cost and failures.
  • Logs: pino JSON (pretty in development), one line per request with the request id.
